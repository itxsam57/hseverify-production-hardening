# M1.06 Subunit 2 Regression Addendum

These stable IDs extend the HSE Verify regression register for defects discovered while building M1.06 Subunit 2. They remain permanent even if the upload/quarantine implementation is later refactored.

| ID | Defect prevented | Root cause | Required behaviour | Permanent automated guard | Status |
|---|---|---|---|---|---|
| REG-039 | A security regression test fails or passes based on which database trigger happens to reject a prohibited post-quarantine mutation first | The first quarantine platform test asserted the exact provenance-guard error text, but the accepted lifecycle guard correctly rejects an in-place quarantined-row update before the provenance-specific branch is reached | Tests must assert the security outcome: the mutation is rejected and the persisted lifecycle/hash/size remain unchanged. Trigger ordering or internal error wording is not part of the security contract | `tests/platform/secure-file-upload-quarantine.test.mjs` rejects the tamper then re-reads and proves the accepted hash/size/lifecycle are unchanged | PROTECTED |
| REG-040 | A trusted upload policy silently accepts duplicate content-kind declarations and canonicalizes them, hiding malformed policy construction | The initial policy constructor compared canonical unique kinds with `new Set(...).size`, which does not detect repeated identical input values | Trusted policy creation must fail closed when the caller supplies any duplicate allowed kind; accepted policies contain unique canonical kinds only | `secure-file-upload-domain.ts` checks set size against input length; `secure-file-upload-domain.test.mjs` rejects `['pdf','pdf']` | PROTECTED |
| REG-041 | Quarantine metadata and its material audit fact appear independently correct in SQL tests but the real repository transaction is never executed under an audit failure | The first candidate tested the transition SQL and audit vocabulary separately, leaving the repository's atomicity claim protected only by source inspection | The actual `DatabaseSecureFileUploadRepository` must be executed against PGlite: success creates one audit fact, replay does not duplicate it, copied/revoked authority is denied, and a forced audit-insert failure rolls the file row back to `reserved` with no quarantine provenance | `scripts/run-secure-upload-runtime-tests.mjs`; `tests/platform/secure-file-upload-runtime.test.mjs` | PROTECTED |
| REG-042 | Legitimate incrementally updated PDFs are rejected merely because they contain more than one historical `%%EOF` marker | The first detector treated a second EOF marker as structural ambiguity even though the frozen upload contract requires a valid header and a final terminal EOF boundary | The detector may contain earlier EOF markers from incremental revisions; it must bind to the final EOF marker and reject only missing terminal EOF or non-whitespace bytes after that final boundary | `secure-file-upload-domain.test.mjs` accepts an incremental two-EOF PDF and still rejects content appended after the final EOF | PROTECTED |
| REG-043 | A PNG with correct signature/chunk lengths/IEND but corrupted chunk data or CRC is accepted as structurally valid | The first parser validated chunk boundaries and terminal IEND but ignored the PNG CRC field | Every parsed PNG chunk must have a valid CRC over its type+data; corrupted CRC, truncation, or trailing bytes fail closed | `secure-file-upload-domain.ts` validates CRC32 for every chunk; `secure-file-upload-domain.test.mjs` mutates an IHDR CRC byte and requires `invalid_structure` | PROTECTED |
| REG-044 | A JPEG wrapper with SOI/EOI and marker-shaped bytes but no actual image frame or scan is accepted as a valid evidence image | The first JPEG detector only searched for SOI and a terminal EOI marker | JPEG structural acceptance requires bounded marker segments, at least one valid SOF frame with non-zero dimensions, at least one valid SOS scan header, scan marker handling and a terminal EOI exactly at the end | `secure-file-upload-domain.ts` parses JPEG markers/frame/scan boundaries; `secure-file-upload-domain.test.mjs` accepts a bounded frame+scan fixture and rejects a wrapper-only JPEG | PROTECTED |
| REG-045 | A PNG with valid signature and CRCs but impossible IHDR geometry or encoding settings is accepted | The first PNG parser treated a 13-byte IHDR as sufficient without validating its semantic fields | IHDR must have non-zero width/height, a valid bit-depth/color-type combination, compression/filter method zero and interlace 0 or 1; repeated IHDR and non-consecutive IDAT sequences fail closed | `secure-file-upload-domain.ts` validates IHDR semantics and IDAT ordering; `secure-file-upload-domain.test.mjs` rejects a zero-width CRC-valid PNG | PROTECTED |

The central regression register should preserve these IDs when next consolidated.
