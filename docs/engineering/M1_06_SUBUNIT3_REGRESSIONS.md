# M1.06 Subunit 3 Regression Addendum

These stable IDs extend the HSE Verify regression register for defects discovered while building M1.06 Subunit 3. They remain permanent even if the malware-scan implementation is later refactored.

| ID | Defect prevented | Root cause | Required behaviour | Permanent automated guard | Status |
|---|---|---|---|---|---|
| REG-046 | A scan handler and terminal outbox recovery acquire the same two rows in opposite order, creating an avoidable database deadlock and allowing copied lease fields to masquerade as trusted worker authority | The first handler repository draft locked the secure-file row and only then checked/locked the outbox lease, while the outbox terminal-failure transaction necessarily locks the outbox row before its recovery trigger updates the linked secure file; the draft also structurally compared lease fields without proving the lease object came from the accepted worker authority | Every handler load/finalize path must require the non-copyable trusted outbox lease capability and must acquire/validate the outbox lease row before locking the secure-file row. Terminal-failure recovery and normal handler finalization therefore use the same outbox→file lock order, and forged copied lease objects fail before mutation | `scripts/check-secure-file-scan.mjs` asserts trusted-lease use and outbox-before-file source order; Subunit 3 runtime tests execute active/stale/reclaimed lease behavior and terminal recovery | PROTECTED |
| REG-047 | A malicious, retryable or terminal scanner outcome persists the result code `clean`, creating contradictory durable evidence even though the file lifecycle is not available | The initial result-code normalizer validated syntax and bounds but did not reserve the semantic `clean` code exclusively for a clean scanner outcome | Only `{ kind: "clean", code: "clean" }` may use the `clean` result code. Malicious, retryable and terminal outcomes must reject `clean` before any result can be persisted or returned to the worker | `src/lib/secure-files/secure-file-scan-domain.ts` uses the non-clean code normalizer; `tests/secure-files/secure-file-scan-domain.test.mjs` rejects `clean` for all non-clean outcomes | PROTECTED |
| REG-048 | A legitimate fixed scanner job extension is mistaken for an unexpected outbox vocabulary change, or the scan payload later grows browser/provider-controlled authority | The accepted outbox unit regression encoded the pre-Subunit-3 three-job list and stopped at email delivery; it had no exact scanner payload cases | The outbox job vocabulary remains exact and wildcard-free and now contains exactly `platform.foundation.noop`, `notification.portal.foundation`, `email.delivery.foundation`, and `secure_file.scan`. A scan job payload contains only the opaque secure-file reference and bounded generation and rejects provider, object key, content hash and arbitrary extra fields | `tests/outbox/outbox-domain.test.mjs` asserts the exact four-job vocabulary, type-separated idempotency and the fixed scan payload allow/deny matrix | PROTECTED |
| REG-049 | Durable `secure_file.scan` jobs can be enqueued and claimed but never execute the scanner handler | The scan handler was implemented as a separate module but the shared fixed outbox handler registry still contained only noop, notification and email jobs | The shared worker must register exactly one static `secure_file.scan` handler that receives the trusted claimed job and lease. Handler selection must remain code-owned and must never use a persisted/browser-selected module, provider or URL | `tests/outbox/outbox-worker-handler-contract.test.mjs` and `scripts/check-secure-file-scan.mjs` require the explicit static handler entry and reject dynamic handler loading | PROTECTED |
| REG-050 | Scanner tests exist in the repository but the normal engineering gate never executes them, allowing a false green release | The first Subunit 3 candidate added source/unit/runtime/migration tests without adding their commands to `package.json` aggregate verification scripts | `check:secure-scan`, unit scan tests, migration-stack tests, scheduler runtime tests and handler runtime tests must all be registered and reachable from the accepted quick/unit/integration/full application gates as applicable | `scripts/check-secure-file-scan.mjs` parses `package.json` and proves each scanner command plus its aggregate-gate membership; the full CI runs those aggregates | PROTECTED |
| REG-051 | The scanner source guard rejects a correctly wired quick gate or forces the same unit suite to run twice | The first aggregate-reachability assertion required `verify:quick` to invoke `test:secure-scan` directly even though the accepted quick gate invokes `test:unit`, which already contains `test:secure-scan` | Scanner coverage must be proven through the real aggregate dependency chain: `verify:quick` directly runs `check:secure-scan` and `test:unit`; `test:unit` runs `test:secure-scan`. The guard must not require redundant leaf execution | `scripts/check-secure-file-scan.mjs` asserts the aggregate chain separately and the full CI executes it | PROTECTED |
| REG-052 | Worker-only scanner tests falsely certify tenant isolation while Company-scoped files can cross tenant or membership boundaries | The initial runtime suite exercised Worker owner/copy denial but did not execute the Company branch of the scheduler’s tenant/membership guard | A Company principal may schedule a Company-scoped file only when account, active role, active tenant, exact active membership, file owner and file tenant/membership all match. Another Company, copied tenant/membership context or a suspended membership must fail without mutating the file or creating another scan job | `tests/platform/secure-file-scan-company-isolation.test.mjs` executes the real repository on PGlite and `scripts/run-secure-scan-runtime-tests.mjs` includes it in the scanner runtime gate | PROTECTED |
| REG-053 | Durable scan state says a file is available while carrying a malicious/failure result, or says unsafe/failed while carrying the reserved `clean` result | The first database scan-shape constraint required only a non-null result for final states, so runtime semantic validation could be bypassed by trusted/internal SQL or another server repository caller | Result meaning is enforced twice: repository finalization rejects contradictory decisions before persistence; database lifecycle shape and update guard require `available + clean` and forbid `clean` for `unsafe` or `scan_failed` | `tests/platform/secure-file-scan-result-semantics.test.mjs` attempts contradictory direct database transitions and proves they fail closed; the scan repository normalizes final decisions before SQL | PROTECTED |
| REG-054 | The real scan scheduler/terminal-recovery regression aborts after valid state transitions because its verification query references a nonexistent outbox sequence column | The new scanner runtime test guessed `outbox_sequence` instead of using the accepted outbox table’s canonical `job_sequence` column | Scanner runtime proofs must query the accepted outbox schema exactly and must never invent sequence aliases. Historical job ordering is verified by `job_sequence`, leaving production behavior unchanged | `tests/platform/secure-file-scan-runtime.test.mjs` orders the two scan generations by canonical `job_sequence`; CI executes the test through `test:secure-scan-runtime` | PROTECTED |

Additional defects discovered by CI or self-review must receive the next stable regression ID before Subunit 3 can close.
